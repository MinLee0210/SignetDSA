# PEM/DER Import-Export

Four algorithms — [RSA](../algorithms/rsa.md), [DSA](../algorithms/dsa.md),
[ECDSA (P-256)](../algorithms/ecdsa.md), and [EdDSA (Ed25519)](../algorithms/eddsa.md)
— expose PEM import/export on their typed API, for interop with keys
generated by OpenSSL or any other PKCS#8-speaking tool. Each has the same
four methods:

```rust
private_key_to_pem(&PrivateKey)   -> Result<String, Error>
private_key_from_pem(&str)        -> Result<PrivateKey, Error>
public_key_to_pem(&PublicKey)     -> Result<String, Error>
public_key_from_pem(&str)         -> Result<PublicKey, Error>
```

## Example

```rust
use SignetDSA::algo::eddsa::EdDsa;
use SignetDSA::Signature;

let (private_key, public_key) = EdDsa::generate_keys();

let private_pem = EdDsa::private_key_to_pem(&private_key).unwrap();
assert!(private_pem.starts_with("-----BEGIN PRIVATE KEY-----"));

let public_pem = EdDsa::public_key_to_pem(&public_key).unwrap();
assert!(public_pem.starts_with("-----BEGIN PUBLIC KEY-----"));

// Round-trip and use normally:
let restored_private = EdDsa::private_key_from_pem(&private_pem).unwrap();
let restored_public = EdDsa::public_key_from_pem(&public_pem).unwrap();

let signature = EdDsa::sign(&restored_private, b"hello").unwrap();
assert!(EdDsa::verify(&restored_public, b"hello", &signature).unwrap());
```

The same four methods, with the same behavior, exist on `Rsa`, `Dsa`, and
`Ecdsa`.

## Why Always PKCS#8/SPKI

Private keys are always encoded as **PKCS#8**
(`-----BEGIN PRIVATE KEY-----`) and public keys as **SPKI**
(`-----BEGIN PUBLIC KEY-----`) — the modern, algorithm-agnostic formats, as
opposed to algorithm-specific legacy formats some older tools still expect
(RSA's traditional `-----BEGIN RSA PRIVATE KEY-----`, for instance). This
keeps all four algorithms' PEM output shaped identically regardless of which
one you're using, and matches what `openssl genpkey` produces by default
for a new key today.

!!! note "This is about key encoding, not the signature scheme"
    Choosing PKCS#8 for the PEM *encoding* is independent of each
    algorithm's *signature* scheme — RSA signatures here are still produced
    with PKCS#1 v1.5 padding as described on [its own page](../algorithms/rsa.md);
    only how the key bytes are wrapped on disk changed to the modern format.

## How This Is Wired Up

Under the hood, this crate depends directly on the
[`pkcs8`](https://docs.rs/pkcs8) crate (in addition to what `rsa`, `dsa`,
`p256`, and `ed25519-dalek` already pull in transitively) purely to enable
its `pem` Cargo feature. `dsa` in particular has no feature flag of its own
for this — it re-exports `pkcs8` as a bare module
(`pub use pkcs8;`) with no `#[cfg(feature = "pem")]` gating on that
re-export, so once *any* crate in the dependency graph turns `pkcs8`'s own
`pem` feature on, Cargo's feature unification means every crate sharing that
one resolved `pkcs8` instance gets `EncodePrivateKeyPem`/
`DecodePrivateKeyPem` for free — including `dsa`, which has no way to
request it itself.

## What's Not Covered

The `Signet` factory's own key serialization (used by
`generate_keys()`/`sign()`/`verify()` on `SignetSigner`) is unrelated to
this — it uses each algorithm's own compact native encoding (raw scalar
bytes, SEC1 points, PKCS#1 DER, and so on), not PKCS#8 PEM. See
[Factory API](factory.md). [ECDSA (secp256k1)](../algorithms/ecdsa_secp256k1.md),
[Ed448](../algorithms/ed448.md), [Schnorr](../algorithms/schnorr.md), and
[BLS](../algorithms/bls.md) don't have PEM helpers — their underlying crates
either don't support PKCS#8 for these key types or weren't wired up for it
here.
