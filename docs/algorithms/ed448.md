# Ed448

**EdDSA over Curve448** ("Ed448", RFC 8032 §5.2) is Ed25519's higher-security
sibling — the same deterministic design, over a larger curve ("Goldilocks")
that targets roughly 224-bit security instead of Ed25519's ~128-bit, at the
cost of larger keys and signatures. SignetDSA uses
[`ed448-goldilocks-plus`](https://docs.rs/ed448-goldilocks-plus).

!!! warning "Known limitation"
    `ed448-goldilocks-plus` is a less battle-tested implementation than
    `ed25519-dalek` — no independent security audit, a much smaller
    deployment base. This crate verifies it against the official RFC 8032
    §7.4 test vectors (see below), but prefer [Ed25519](eddsa.md) unless
    Ed448's larger security margin is specifically required.

!!! note "Why plain `ed448-goldilocks` (no `-plus`) isn't used"
    As of version 0.9, the original `ed448-goldilocks` crate is curve
    arithmetic only — no EdDSA sign/verify at all. `ed448-goldilocks-plus`
    is the actively maintained fork that adds the actual signature scheme
    this crate needs.

## Why Key Generation Looks Different Here

`ed448-goldilocks-plus` depends on `rand_core` 0.10, while the rest of this
crate (and its `rand::rngs::OsRng`) is on the `rand` 0.8 / `rand_core` 0.6
generation — an incompatible *trait*, not just an incompatible version, so
`OsRng` can't be passed directly to the crate's own `SigningKey::generate`.
Rather than pull in a second `rand_core` major version crate-wide,
`Ed448::generate_keys` fills 57 bytes from the same `OsRng` every other
module here uses and hands them to `SigningKey::from_bytes` — which is
exactly what `generate` does internally, just with the randomness sourced
one level up.

## Pseudocode & Complexity

Ed448 follows the exact same shape as [Ed25519's algorithm](eddsa.md#the-algorithm)
— clamp a hashed seed into a scalar, derive a per-message nonce from a
secret-derived prefix, sign as $(R, S)$, verify $SB = R + kA$ — with two
concrete differences:

```text
KeyGen():
    seed        <- 57 random bytes                    # not 32, like Ed25519
    (s, prefix) <- split(SHAKE256(seed, 114 bytes))    # XOF, not SHA-512
    A           <- s * B
    return (private_key = seed, public_key = A)

Sign(seed, message):
    (s, prefix) <- split(SHAKE256(seed, 114 bytes))
    r <- SHAKE256("SigEd448" || 0x00 || 0x00 || prefix || message, 114 bytes) mod L
    R <- r * B
    k <- SHAKE256("SigEd448" || 0x00 || 0x00 || R || A || message, 114 bytes) mod L
    S <- (r + k * s) mod L
    return (R, S)

# Verify: identical shape to Ed25519, substituting SHAKE256 for SHA-512.
```

The `"SigEd448" || 0x00 || 0x00` prefix folds in the (empty, in this
crate) context string and prehash flag — see
[why key generation looks different](#why-key-generation-looks-different-here)
above for why `SigningKey::from_bytes` is used here instead of `generate`.

**Complexity** is the same $O(\log L)$-point-operations shape as
[Ed25519](eddsa.md#complexity) (one fixed-base multiplication for KeyGen and
Sign, one fixed- plus one variable-base multiplication for Verify) — but
each individual point operation costs measurably more, because Curve448's
field is 448 bits wide versus Curve25519's 255, so every field
multiplication underneath each point operation has roughly $(448/255)^2
\approx 3\times$ more schoolbook-multiplication work. That per-operation
constant, not a difference in asymptotic class, is why Ed448 is
noticeably — not just proportionally-to-key-size — slower than Ed25519 in
practice.

## How to Use

### Typed API

```rust
use SignetDSA::algo::ed448::Ed448;
use SignetDSA::Signature;

let (private_key, public_key) = Ed448::generate_keys();
let message = b"Hello, SignetDSA!";

let signature = Ed448::sign(&private_key, message).expect("signing failed");
assert!(Ed448::verify(&public_key, message, &signature).unwrap());
```

Keys and signatures are fixed-width: a 57-byte private key, a 57-byte public
key, a 114-byte signature — noticeably larger than Ed25519's 32/32/64.

### Factory API

```rust
use SignetDSA::{Signet, SignetSigner};

let signer = Signet::from_name("ed448").unwrap(); // alias: "ed448-goldilocks"
let (sk, pk) = signer.generate_keys(); // 57-byte seed, 57-byte point
let sig = signer.sign(&sk, b"Hello, world!").unwrap();
assert!(signer.verify(&pk, b"Hello, world!", &sig).unwrap());
```

## Interoperability

Ed448 is checked against the official
[RFC 8032 §7.4](https://www.rfc-editor.org/rfc/rfc8032#section-7.4)
context-free ("PureEdDSA") test vectors in
[`tests/rfc8032_ed448.rs`](https://github.com/MinLee0210/SignetDSA/blob/main/tests/rfc8032_ed448.rs).
Signing and verification go through the crate's `sign_raw`/`verify_raw`,
which correspond exactly to those vectors (phflag 0, empty context) — not
the `Ed448ph` prehashed variant or the context-carrying variant, neither of
which this crate exposes.

## Errors

`Ed448::Error` is `Ed448Error`, with variants for invalid signature
encoding, invalid public key encoding, and verification failure.

## When to Use

Reach for Ed448 only when you specifically need its larger security margin
over [Ed25519](eddsa.md) — larger keys/signatures and a less mature
implementation are real costs, not free upside.
